## 1. 문제점 (반복 빈도 순)

### ① 여러 적에게 동시에 붙는 싸움 — 가장 큰 사망 원인
- 관련: P-6, P-7, P-8, P-26, P-29(같은 자리에서 2번 사망), P-45, P-46, P-47
- 증상: 둘 이상이 붙으면 "공격 0번, 받은 피해 수백"으로 끝난다.
- 구조 원인: `duel`은 기본이 1:1이고 "목표 바꿈"·"벽으로 물러나기"를 덧붙인 형태다.
  - 둘러싸였을 때 물러나기는 P-26 이후 꺼져 있다 (`CROWD_FALL_BACK = False`, 반복 상한만 있음).
  - 잘 된 방법은 MoKa가 구역마다 손으로 정한 "안전 자리로 하나씩 끌어오기"(`burg-upper`, `TOWN_ENTRY.md`)뿐이다.
    이것이 일반 규칙이 아니라 구역별 데이터(`data/burg-upper-map.json`)로만 들어가 있어, 새 구간마다 사람이 다시 정해야 한다.

### ② 걷기 제어가 고정 규칙이라 같은 자리에서 반복해서 막힘
- 관련: P-12(`#3 이동` (−52.2,−22.8,−26.9)가 12번 넘게 AGAIN, 상자 `o1150_01`·`o1132_06`), P-17(보류), P-28, P-42, 1-f
- 고칠 때마다 다른 곳이 망가졌다. 27x: 천천히 걷게 바꾸자 도착 반경 0.5 m 안에 못 들어가 시간 초과 → 되돌림.
- MoKa 진단(1-g): "NavMesh 모양 → 속도·턴을 배우는 구조가 없다." 걷기는 점·반경·스틱 세기를 사람이 정한 규칙이다.
- 6-a 하네스가 측정 도구를 만들었다: 급코너 666번 중 48 %가 모퉁이 안쪽으로 0.5 m 넘게 지나감.

### ③ 낙사·가장자리
- 관련: P-14, P-16, P-19, P-30, 10-06 경사로 낙사(`d9032a3`)
- 바닥 확인이 상황별로 따로 붙어 있다 (뒤잡기 전·중·후, 물러날 때, 턱 되돌림).
- 3번 "충돌 메시"는 시작 전 → 매 틱 앞길을 미리 확인하는 공통 장치가 없다.

### ④ 적 종류별 반응 타이밍을 손으로 맞춤

### ⑤ 스스로 배우는 구조와 평가 데이터가 없음

## 2. 공개 사례 — 비슷한 문제를 푼 방법

| 우리 문제 | 사례 | 가져올 점 |
|---|---|---|
| ② 모퉁이 감속·도착 반경 | **Nav2 Regulated Pure Pursuit** ([문서](https://docs.nav2.org/configuration/packages/configuring-regulated-pp.html)) | 곡률이 크면 속도를 줄이고(`use_regulated_linear_velocity_scaling`), 목표 근처에서 감속하되 최저 속도를 따로 둔다(`min_approach_linear_velocity`). 27x의 "느리게 했더니 도착 못 함"을 막는 설계. |
| ② 같은 자리 막힘 | Nav2 **SimpleProgressChecker** (`required_movement_radius 0.5`, `movement_time_allowance 10 s`) | 자리마다 고치지 않고 "진행이 없으면 다시 계획" 하나로 처리. `track_report`의 멈칫 판정을 걷기 루프 안으로 넣는 것과 같다. |
| ② 모퉁이 안쪽으로 꺾음 (P-17) | **Recast/Detour `dtPathCorridor`** ([API](https://recastnav.com/classdtPathCorridor.html)) — `findCorners`, `optimizePathVisibility` | 고정 경로 점을 따라가지 않고 매 틱 "보이는 가장 먼 모퉁이"를 다시 계산. |
| ② 부서지는 상자 (P-12) | **Baritone** (Minecraft) ([FEATURES](https://git.psf.lt/0xf8/baritone/src/commit/008422680dfd03b220cbb44f87f548f3549a3631/FEATURES.md)) | 부수기를 경로 탐색 비용에 넣는다. 지금 `props.steer_around`는 경로를 만든 뒤 고치는 방식. |
| ③ 낙사 | Baritone (떨어지는 높이를 비용·한도로), Nav2 RPP (앞으로 그린 호 위 충돌을 미리 확인 → `NoValidControl`) | 상황별 바닥 확인을 "매 틱 앞으로 0.5~1 s 갈 길 확인" 하나로. |
| ② 막힘 감지 (참고) | **mineflayer-pathfinder** "Detect bot is not moving and reach other way" ([이슈 목록](https://issuehunt.io/r/PrismarineJS/mineflayer-pathfinder?tab=idle)) | 큰 프로젝트도 열려 있는 문제. 위치를 감시하다 다시 계획하는 방식이 사실상 표준. |

| ④ 반응 타이밍 | **TekkenBot** ([wT-/TekkenBot](https://github.com/wT-/TekkenBot)) — 메모리에서 동작 ID를 읽고 프레임 데이터 표로 판단 | `foes.py`와 같은 방식. 차이는 표를 손으로 재지 않고 게임 데이터에서 뽑는 점 → ROADMAP 7(TAE 추출). |
| ⑤ 학습 | **SoulsGym** ([amacati/SoulsGym](https://github.com/amacati/SoulsGym)), **EldenRL** ([fork](https://github.com/CyberDatta/EldenRL_mysystem)) | 둘 다 보스 1:1 아레나에서만 된다. SoulsGym은 메모리로 HP를 고정하고 3000스텝마다 리셋하며, 시드로 재현되지 않는다고 밝힌다. 여러 적이 있는 필드 학습은 공개 사례 없음 → 6-a 하네스 + MoKa 시범 흉내 학습이 현실적. |

## 3. 제안 (우선순위)

1. **여러 적 = 자리 선택 문제로 일반화.** "동시에 닿을 수 있는 적 ≤ 1"을 만족하는 자리로 물러나거나 끌어오는 공통 규칙.
   `burg-upper` 안전 자리 데이터는 그 규칙의 입력(후보 자리)으로 쓴다. 사망의 절반 이상이 여기서 나온다.
   확인: P-29 자리(`#4 이동`)와 `burg-upper` 구역 4·5·8을 구역 데이터 없이 통과하는지.
2. **걷기에 Nav2 RPP식 구조 세 가지** — 곡률로 감속, 도착 근처 최저 속도 보장, 진행 감시 → 다시 계획.
   `_follow` 안에서만 바꾸고 6-a 하네스(`walksim.py`)로 P-17 전후·27x 시간 초과를 재현해 비교 → [win] A/B.
3. **바닥 확인을 하나로** — 매 틱 앞으로 갈 길(0.5~1 s)의 바닥을 NavMesh로 확인하는 공통 장치. 3번 충돌 메시의 작은 첫걸음.
4. **사람 확인 장면을 회귀 테스트 기대값으로** — 예: P-33의 세 장면은 guard만 허용. golden이 규칙 자체를 검증하게 된다.
5. **실행 설정 기록 결정** — `<run>.settings.json`과 로그의 `code_commit`. 위 1~4의 A/B 비교가 믿을 만해진다.
6. **ViGEm 대안 조사(낮음)** — 보관된 드라이버라 Windows 업데이트로 깨질 수 있음. 지금은 P0 안전장치로 충분.

# v1.0 → v2.0 리뷰 (2026-10-11, [cloud])

범위: 최근 7일(10-04 ~ 10-11) 커밋 82개, ROADMAP 열린 항목, 문제 기록 P-44 ~ P-58, `souls/`·`run.py` 코드 구조.
지금 봇을 v1.0으로 볼 때 v2.0에 구조 개선이나 기능 추가가 필요한지 본다. `docs/analysis-2026-10-09.md`의 이어짐이며,
이 문서도 **분석과 제안**이다 — 확정된 계획이 아니며, 정해진 것만 ROADMAP으로 옮긴다.

**결론: 2.0은 필요하다. 새 기능보다 구조 개선이 먼저다.** 사람이 짚어준 경로에서는 잘 통과하지만(셀 → Burg 화톳불 한 번에,
`burg-upper` 구역 1~8), 새 구간이나 조금 다른 상황마다 사람이 다시 손을 대야 한다. 최근 7일 커밋이 그 한계를 그대로 보여준다.

기준 상태: 작업 브랜치 `c8471d5`, 오프라인 테스트 `python -m pytest` 79개 모두 통과 (4분 28초, Linux).

## 2. 구조 문제 (2.0의 핵심)

### ① `souls/field.py`가 너무 많은 일을 한다
- 2,091줄, 함수 89개, `while` 루프 37곳.
- 걷기·싸움·끌어오기·몸으로 끌기·회복이 각자 자기 루프를 돌며 게임 상태를 따로 읽는다.
- 그래서 "걷는 중에 적이 붙음"(P-45), "걷기 틱 안의 반사 순서"(ROADMAP 2 [win] 항목) 같은 문제가 루프마다 따로 생긴다.
- `--ground`가 "걷기에선 새 바닥 지도, 싸움·회복·반사에선 원래 NavMesh"(`GROUND_IN_FIGHTS = False`)인 것 자체가 증상이다 —
  같은 바닥을 상황마다 다른 방법으로 판단한다.
- **2.0 방향:** 틱 루프 하나. 매 틱 "읽기 → 상태 갱신 → 행동 하나 고르기 → 입력". 바닥·물러나기·반사 확인은 그 한 곳에서 하고,
  걷기·싸움은 그 루프가 고르는 하위 행동이 된다.

### ② 경로 지식이 코드 안에 있다
- 구역 8 사다리, 구역 1 화톳불 휴식 같은 처리가 `souls/missions.py`의 `_before`·`upper_segment`에 있다.
- `data/burg-upper-map.json`의 적마다 다른 방법(`wait`, `lure_at`, `attack`)과 섞여 있다.
- 새 구간 하나에 MoKa 녹화 → [cloud] 코드 → [win] 실행이 몇 번씩 돈다.
- **2.0 방향:** 경로를 데이터로 적는다 (걷기 / 조심 걷기 / 안전 자리 / 끌기 / 싸움 / 사다리 / 안개벽 / 에스트 기준).
  공통 실행기가 그 데이터를 읽어 실행 → 새 구간은 코드 수정 없이 데이터만 추가.

### ③ 설정이 모듈 전역 변수로 흩어져 있다
- `souls/field.py`·`duel.py`·`missions.py`·`escape.py`·`pull.py`에 대문자 상수 228개.
- `run.py`가 실행 중에 직접 바꾼다: `duel_.BACKSTAB`, `duel_.HEAVY`, `field_.NOTICE_PULL` …
- 그 밖의 켜기/끄기: `ESCAPE_PICK`, `SEP_ESCAPE`, `GROUND_IN_FIGHTS`, `CROWD_FALL_BACK`, `WALL_BACK` …
- `runinfo`가 값을 기록해주지만, A/B 비교와 테스트가 전역 상태에 기댄다.
- **2.0 방향:** 설정 객체 하나를 만들어 넘긴다. 실행 설정 기록은 그 객체를 그대로 저장.

### ④ 게임 상태와 봇의 기억이 어긋난다 (P-18, P-25, P-44, P-55)
- 퀵 종료·워프·화톳불 휴식 뒤 "누가 살아있나"를 기능마다 따로 처리한다.
- **2.0 방향:** 한 객체(WorldState)에 모으고, 화톳불 휴식·퀵 종료(바이트/메뉴)·워프 사건이 생기면 그 한 곳에서 다시 맞춘다.

### ⑤ 평가 방법이 결과를 가리지 못한다
- `--ground` A/B는 두 번 했지만, 켠 쪽 실행의 상당수가 통로에 닿기도 전에 경사로에서 죽어 비교가 안 됐다
  (2라운드: 켠 쪽 3번 중 통로까지 간 것 1번).
- **2.0 방향:** 세이브 복원·워프·N회 반복·`ab.py` 보고를 한 번에 돌리는 일괄 실행기. "구간별 통과율 n/10" 같은 지표로 판단.

### ⑥ 싸움 규칙 27개를 위에서부터 첫 일치로 고른다 (`souls/duel.py` 1,627줄)
- 장면 기대값 테스트(제안 4)로 지키는 방향은 맞다.
- 다만 적 반응표(`souls/foes.py`)를 손으로 맞추는 한 새 적마다 P-46 같은 일이 반복된다 → 길게는 게임 데이터(TAE)에서 뽑는다.

## 3. 2.0에 넣을 기능 (우선순위)

1. **여러 적 = 자리 고르기 (제안 1, `docs/design-multi-foe-spot.md`).** 가장 큰 사망 원인. MoKa의 안전 자리는 "후보 데이터"로 내리고 자리는 봇이 계산.
2. **모든 상황에서 같은 바닥 확인.** 한 틱 루프 위에서 `Ground` + 가장자리 분류(충돌 메시). P-49·P-58 경사로 턱 낙사 계열.
3. **보스 싸움 모듈.** 타우로스가 첫 사례 (사다리 → 송진 → 낙하 공격 → 약공). 필드 1:1과는 다른 루프.
4. **원거리 적 처리 마무리.** `rule_shot` 게임 확인과 #4 원거리 적 분류 수정.
5. **죽은 뒤 이어하기.** 임무 진행 상태 저장, 혈흔 회수 뒤 끊긴 구간부터 다시.
6. **학습(1-g)은 2.0에 넣지 않는다.** 위 평가 체계가 먼저 있어야 의미가 있고, Laya는 이미 "불필요" 결론(10-02).

## 4. 2.0 완료 기준과 순서 (제안)

**완료 기준 (예시 — 숫자는 MoKa가 정함)**
- Burg 화톳불 → 타우로스 처치, 10번 중 N번 사망 없이 성공
- 새 구간을 구역 코드 없이 경로 데이터만으로 추가
- 바닥·물러나기·반사 확인이 틱 루프 한 곳에서만 일어남

**순서**
1. 지금 상태를 `v1.0` 태그로 고정.
2. 설정 객체와 WorldState. 작고 위험이 낮다.
3. 한 틱 루프로 옮김. 한 번에 버리지 않고 걷기부터 한 부분씩 옮기며, `scene_replay`·`duel_golden_test`로 결정이 바뀌지 않았는지 지킨다.
4. 경로 데이터 형식을 만들고 `burg-upper`를 그 형식으로 옮김.
5. 여러 적 자리 고르기.
6. 일괄 평가 실행기.
7. 보스 싸움.

**위험:** [win]이 게임 테스트를 계속 하는 중에 큰 리팩터를 하게 된다. 1.0이 계속 돌 수 있게 두고 한 부분씩 옮긴다.

**MoKa에게 물을 것:** (1) 2.0을 할지, 한다면 위 순서대로 갈지 · (2) 완료 기준의 숫자(N/10) · (3) `v1.0` 태그를 어느 커밋에 붙일지.

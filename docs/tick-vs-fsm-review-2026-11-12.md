# 틱 규칙 → 상태 머신? 범위·비용 검토 (2026-11-12, [cloud])

요청: MoKa 11-12 "틱 룰을 상태 머신 구조로 바꾸는 게 쉬워? … 아예 다른 버전이 되는 것 같은데?" — win-claude가 보드 스레드
8ccf86e4로 전달 (질문 1–4). **검토 문서만, 코드·RULES는 안 바꿈.** 바탕: [win] 정리 `docs/tick_vs_fsm_pplx_2026-11-12.md`,
`docs/design-clean-motion.md` 28–38줄 (중간안), P-162 · P-164, 저장소 코드 (3fb011e).

검증 수준: 코드 읽기와 파일·테스트 개수 세기뿐. 규모(줄 수)는 어림 — 만들어 본 것이 아님. 게임 확인 없음.

---

## 결론 먼저

- **싸움 층(duel.RULES)을 통째로 상태 머신으로 바꾸면 사실상 새 버전이다.** 테스트 47개 파일이 duel을 직접 쓰고, 그중 17개는 규칙
  함수를 이름으로 부르며, golden 40,320 상황 · MoKa 장면 85개 중 31개 · 실제 실행 장면 재생(scene_replay)이 모두 "규칙 이름"으로 결과를
  잰다. 바꾸는 순간 "예전과 같은가"를 볼 수단이 함께 사라진다.
- **필요한 것은 구조 교체가 아니라 "동작 실행 계약"이다** ([win] 정리·중간안과 같은 결론). 규칙 목록은 그대로 고르는 일을 하고, 고른
  동작이 오래 걸리면 그 동작에 마감·중단 조건·정직한 결과를 붙인다. P-164의 직접 원인이 정확히 여기 (아래 §3).
- **경로 층은 상태 머신(또는 "전제가 있는 단계")으로 가는 게 맞고, 그건 v2.0 `route-data`와 같은 일이다.** 단계 번호 대신 "지금 어디·무슨
  상태인가"로 다음 단계를 고르게 — P-162 · P-160의 원인.

## 1. 층별 규모

### (a) 경로 / 임무 층 → 상태 머신 (또는 전제·결과가 있는 단계)

| | 지금 | 바꾸면 |
|---|---|---|
| 코드 | `souls/missions.py` 1,770줄 (구역 코드 `upper_zone` · `upper_segment` · 사다리 `_before`), `souls/altar.py` 610, `andre_route.py` 460 (단계 목록 30개, 순서대로) | 단계마다 **전제** (어느 층·구역에 서 있나, 문 상태, 살아 있나), **성공 조건**, **실패 시 다음** (지금 구역에서 다시 / 이전 단계로 / 멈춤) |
| 상태가 사는 곳 | 단계 번호 `i` + 각 함수 안 지역 변수 | 세계 상태 (WorldState — 이미 있음, worldstate 1–2단계) + 구역 판정 |
| 깨지는 테스트 | missions · altar · andre_route를 쓰는 26개 파일 (burg_upper · altar_andre · passage_start · ramp_passed · zone8_hold …) — 대부분 "이 구역 함수가 이 순서로 부른다"를 봄 | 구역 하나씩 옮기면 그 구역 테스트만 다시 씀 |
| 규모 (어림) | — | 공통 실행기 + 단계 정의 형식 300–500줄, 구역마다 데이터로 옮기기. `burg-upper` 8구역이 첫 대상 |

- 이건 **v2.0 순서의 4번 `route-data`** ("경로를 데이터로 적고 공통 실행기")와 같은 일. 따로 "상태 머신 프로젝트"로 만들 필요 없음.
- 한 구역씩 옮길 수 있고, 옛 구역 코드는 옮길 때까지 그대로 돈다 — 위험이 낮음.

### (b) 싸움 층 (duel.RULES) → 상태 머신 전면 교체

| 묶여 있는 것 | 개수 | 교체하면 |
|---|---|---|
| duel을 import하는 테스트 | 47 파일 | 대부분 다시 씀 |
| 규칙 함수를 이름으로 직접 부르는 테스트 | 17 파일 | 다시 씀 |
| golden (`duel_golden_test`) | 40,320 상황의 "첫 결정" 스냅숏 | 결정 함수가 바뀌므로 통째 재기록 — "바뀌었나"를 볼 기준이 사라짐 |
| MoKa 장면 (`tests/expect/duel.jsonl`) | 85개: 규칙 이름 31 · 전술 48 · Moves 호출 15 | 전술·호출 63개는 살아남음, 규칙 이름 31개는 새 상태 이름으로 옮겨 적어야 함 |
| 실제 실행 장면 재생 (`scene_replay.py`, `--ctl-scenes`) | [win] 실행 장면 기록 (예: 5 실행 1,144 결정) | "그때와 같은 규칙?"이 규칙 이름 비교라, 옛 기록과 비교 불가 |
| duel.py | 2,993줄, 규칙 35개 | 규칙을 상태·전이로 다시 짜야 함 — 몇 주 단위, 그동안 [win] 게임 확인과 동시 진행 어려움 |

→ **(b) 전면 교체는 새 버전.** 얻는 것(명시적 상태)은 아래 중간안으로 대부분 얻을 수 있음.

### (b') 중간안: 규칙 목록 유지 + 오래 걸리는 동작만 작은 실행기 (`design-clean-motion` 32–38줄)

- duel.py 안에서 **한 틱보다 길게 패드를 쥐는 동작**이 대상: `_separate` (→ `walk_path`, 점마다 2.5 s, 전체 마감 없음), `kick_combo` (4곳),
  연타 `light` (7곳), `heavy` (5곳), 뒤잡기 돌기, `backstep` · `step`, `drink` (2.2 s + 칸 고르기 최대 3 s).
  Field 쪽: `walk_to` · `retreat` · `clear`의 되돌아 걷기 · `recover` · `fall_back` (13개 긴 동작).
- 실행기 계약 (동작마다): **시작 · 매 틱 감시 · 마감 시간 · 중단 조건 (HP 급락, 적이 붙음, 바닥 끝, 진행 없음) · 정직한 결과**
  (`arrived` 대신 `arrived_but_pinned` 같은 사실).
- 깨지는 것: 감싸는 동작의 테스트만 (그 동작의 결과 문자열이 바뀌면). golden · 장면 · scene_replay는 **규칙 선택이 같으므로 그대로** —
  "바뀌었나 / 맞나" 두 기준이 계속 쓰임.
- 규모 (어림): 실행기 틀 100–200줄 + 동작 하나 감쌀 때마다 30–80줄과 테스트. 한 번에 하나씩.

## 3. P-164는 어느 층의 상태가 빠져서인가 (질문 3)

P-164 (run 20261111_235422): 두 적이 0.8–1.3 m에 붙은 채 152.7–157 s에 HP 583 → 0, 기력 69–98, 에스트 10 — 마시지도 구르지도 않음.

코드로 본 경로 (읽기, 게임 재현 아님):
1. `rule_separate` (RULES 3번째) → `_separate` → `mv.walk_path(way, …, stop=cancel, timeout_per=2.5)`.
   **걷는 동안 다른 규칙은 하나도 안 돈다** — 반사·막기·에스트 모두. 멈추는 조건은 `cancel()` (싸움 밖 사정)뿐, HP·붙은 적은 안 봄.
2. `walk_path`가 `arrived`(또는 escape `arrived`)를 돌려주면 성공으로 기록 — **두 적이 여전히 붙어 있는지 안 봄** (거짓 성공).
3. 한 싸움에 `SEP_MAX` 3번, `SEP_COOLDOWN` 5 s — 그 사이 틱은 다른 규칙이 돌지만, 그때 HP는 50 % 아래였고 당시 규칙으로는
   (andre_route의 clear가 desperate로 부른 싸움이면) 에스트 길이 `rule_estus` (HP 50–60 %에만 열림)뿐 → 마실 길 없음.
4. 바깥 층: `andre_route`의 `clear` → `Field.fight` 한 번이 14 s — 경로 층은 그동안 다시 판단 못 함.

→ **빠진 것은 "동작 층"의 감시 (1, 2)와 HP 정책 (3)** 이고, 규칙 선택 구조 자체가 아님. 오늘 바뀐 것 중 관련: M1112-02
`rule_low_sip` (30 % 밑 바로 마심)이 RULES 맨 앞 — 3번은 30 % 밑에서는 메워짐 (P-164의 245 HP = 29 %에서 걸렸을 것). 단 1번
(walk_path 안)에서는 여전히 안 돎 — 동작 실행기가 필요한 이유.

## 4. 추천 순서와 성공 기준 (질문 4) — MoKa 결정 전, 만들지 않음

1. **기록부터** (행동 안 바뀜): 틱마다 고른 규칙 · 실행 중인 동작과 나이 · 패드를 쥔 쪽. `blind_report` (판단 공백 > 2 s)가 이미 일부.
   성공: P-164 같은 실행에서 "152–157 s 동안 무엇이 패드를 쥐었나"가 로그 한 줄로 나옴.
2. **`_separate` 하나만 실행기로**: 전체 마감 (예: 3 s) · HP가 이 동작 중 X 넘게 줄면 중단 · 끝에 "붙은 적 수"를 다시 보고
   `arrived_but_pinned`면 실패로. 성공: 가짜 세계 테스트 "두 적이 따라붙는 떼어놓기" → 마감 안에 끝나고 다음 틱에 다른 규칙 (에스트 ·
   구르기)이 돎; golden · 장면 · scene_replay 변화 없음.
3. **Field의 긴 걷기** (`retreat` · `clear` 되돌아 걷기) 같은 틀로. 성공: 같은 종류 테스트 + 게임 1–2회에서 판단 공백 최대치 감소.
4. **경로 층 = v2.0 `route-data`**: `burg-upper` 8구역부터 "전제 · 성공 · 실패 시" 단계로. 사다리 단계는 "위층에 섰나"를 전제로 (P-162).
   성공: 떨어지면 위층 단계를 안 하고 지금 구역에서 다시 이음 — 가짜 세계 테스트 + 게임.
5. **v2.0 `tick-loop`**은 "틱 루프 하나 + 동작 실행기"로 정의를 고쳐 쓰기 — 상태 머신 전면 교체가 아님.

전체 성공 기준 (게임): v2.0 완료 기준 그대로 (클레이모어 세이브, 지금 3번: burg-upper ≥ 2/3, 타우로스 ≥ 1/3, 사망만 실패, 회수 없음
— M1111-36~41), 거기에 **판단 공백 최대치**(blind_report)와 **거짓 성공 0**(동작 결과가 끝난 뒤 세계와 맞는지)을 같이 봄.
